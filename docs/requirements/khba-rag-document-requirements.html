1 · Why this doc exists

The current POC ingests PDF source files through LlamaCloud's agentic OCR. In production, a large share of Korean legal/administrative source material — ordinances, internal association guides, member case files — is authored and circulated as HWP (한글, Hancom's proprietary format), not PDF. The ingestion pipeline needs a defined path for that format before real documents can be loaded.

This is a separate plan from the POC implementation doc: it covers what document types the system must accept, why HWP is hard, the candidate solutions, and the resulting API list for budgeting and integration work.

2.2 Per-document metadata required at intake

To populate the WS-1267 document / document_version tables, every ingested file — regardless of source format — must arrive with:

  • documentCode, title, authorityType, jurisdictionCode, securityClass, version
  • Original file hash (source_hash) for change detection
  • effective_from / effective_to where applicable (laws, ordinances)

2.3 Quality bar for parsed output

Regardless of which HWP solution is chosen, the parsed output must satisfy the same bar the LlamaCloud PDF path already meets:

  • Clean Markdown, tables as pipe tables (not embedded images or HTML)
  • Reading order preserved for multi-column layouts
  • No loss of Korean text encoding (HWP's native encoding requires explicit handling)
  • Article/clause numbering (제3조, 제1항) preserved as plain text so content_node.node_path extraction still works

3 · The HWP problem

HWP is a closed, binary, OLE-compound-document format developed by Hancom — not an open standard like PDF or DOCX. Two practical issues follow:

  • No official cross-platform parser. Hancom's own SDKs and the Windows OLE Automation route assume a Windows host with Hancom Office installed; there's no first-party Linux/serverless parsing path.
  • Legacy .hwp vs. .hwpx. .hwpx is Hancom's newer, XML-based format and is comparatively easy to parse with open tools. Legacy .hwp (binary, "HWPv5") is the harder case and is what most existing archives still use.
Why this matters for solution choice A tool that only handles .hwpx well is not sufficient if the corpus still contains legacy .hwp files.

4 · Proposed solutions for HWP ingestion

4.1
Native SDK
Hancom SDK / Hancom Developer APIs

Hancom provides its own developer platform with an Hwp SDK that can open, convert, and manipulate .hwp/.hwpx files programmatically, plus a document conversion service and OLE Automation guide.

Pros

First-party, most faithful rendering since it's the format owner's own engine; covers both legacy .hwp and .hwpx.

Cons

Commercial licensing; native/per-OS SDK needs a wrapper service; adds an infra dependency not needed today.

4.2
Hosted API
Upstage Document Parse

Upstage's document-digitization REST API natively accepts .hwp and .hwpx and returns structured Markdown/HTML — the same shape our pipeline already expects from LlamaCloud.

Pros

Drop-in REST API — same integration shape as LlamaCloud. Billed per page, no infra to run. Table/layout recognition is a stated strength.

Cons

HWP support is relatively recent — needs validation. Hosted service, so documents leave our infra (relevant for CONFIDENTIAL sources).

4.3
Self-hosted · Open source
pyhwp + a small FastAPI wrapper
Chosen solution

pyhwp is an open-source (AGPLv3) Python library and CLI that parses legacy binary .hwp directly, with no dependency on Hancom software. It can be wrapped in a small internal FastAPI service.

Pros

Free, open source, no per-page billing, fully self-hosted, no vendor lock-in.

Cons

Marked "Experimental" by maintainers; weaker table fidelity; no .hwpx support (legacy .hwp only); we own the wrapper and maintenance.

6 · Recommendation — Decision

Chosen: a self-hosted Java service — hwplib (.hwp) + hwpxlib (.hwpx) Superseded the initial pyhwp + FastAPI implementation (which only handled legacy binary .hwp, not .hwpx) with one self-hosted Java service (./java-hwp) that parses both Hangul formats. Stays free/open-source and in-house.

Known limitation to plan around pyhwp only parses legacy binary .hwp — it does not support .hwpx. Plan for either confirming the corpus is .hwp-only for now, or pairing pyhwp with a lightweight .hwpx path (XML-based, parseable with e.g. lxml) up front.
Implementation notes
  • Build a small FastAPI service (e.g. services/hwp-parser/) exposing POST /parse, wrapping pyhwp's hwp5txt / hwp5html converters.
  • Wire it into lib/ingest/parse.ts as a branch keyed on file extension, alongside the LlamaCloud PDF path — same contract, so chunking downstream is unaffected.
  • Table fidelity is the main known weak point — plan a manual review/cleanup pass on early HWP documents with tables, especially anything feeding chunk_type = TABLE.
  • Because there's no vendor SLA, budget time for maintaining the wrapper and tracking the upstream pyhwp project.
  • Keep Upstage Document Parse and the Hancom SDK documented above as fallback options if pyhwp's output quality proves insufficient.
